# Как залить это на GitHub

## Вариант 1: через сайт (без командной строки)

1. Распакуйте архив `Settled-Lands-repo.zip` в пустую папку.
2. На github.com: **New repository** → имя, например `settled-lands` → Public или Private
   → **Create repository** (без README, он у нас уже есть).
3. На странице репозитория: **uploading an existing file** → перетащите **содержимое**
   папки (все файлы и папки, включая скрытую `.github`) → **Commit changes**.
4. При перетаскивании папок сайт сохранит структуру. Если браузер не берёт скрытую
   `.github`, создайте файл `.github/workflows/build.yml` вручную через **Add file**.

## Вариант 2: через git (удобнее для дальнейших правок)

```bash
cd путь/к/распакованной/папке
git init
git add .
git commit -m "Settled Lands 0.4.4"
git branch -M main
git remote add origin https://github.com/ВАШ_ЛОГИН/settled-lands.git
git push -u origin main
```

## Как публикуется релиз

Готовый JAR в репозиторий **не кладём**: игрок скачивает его со страницы
**Releases** — там всегда одна актуальная версия и не бывает двух JAR в `mods`.
Текущий релиз: **0.5.0** (тег `v0.5.0`, файл `settledlands-0.5.0.jar`, 90 752 байта).

Публикацию делает workflow `publish-release.yml` (**Actions → Publish release →
Run workflow**). Он:

1. скачивает JAR из артефакта `settledlands-jar` указанного прогона `Build`;
2. создаёт релиз с нужным тегом на нужном коммите (`--target`);
3. скачивает **опубликованное** вложение обратно и дописывает в описание релиза
   его размер и sha256 — игрок может сверить скачанное;
4. если релиз с таким тегом уже есть — ничего не делает (повторный запуск безопасен).

Поля запуска: `run_id` (прогон `Build`), `tag`, `target_sha`, `title`, `notes_file`
(файл описания в репозитории, например `RELEASE-NOTES-0.5.0.md`), `artifact_name`,
`dry_run` (только скачать и показать). Описание релиза берётся из `notes_file`;
полный список изменений — из `CHANGELOG-<версия>.md`.

Почему не `gh release create` с локальной машины: JAR, собранный вручную, может
отличаться от проверенного в CI. Берём ровно тот файл, который собрал `Build`, —
поэтому в описании указаны его размер и sha256.

Готовый JAR дополнительно лежит в папке **`release/`** репозитория — оттуда его
удобно скачивать одной ссылкой. Кладет его туда workflow `put-jar-to-release.yml`
(**Actions → Put jar into release folder → Run workflow**, поля `run_id` и `version`):
он берёт JAR из артефакта прогона `Build`, прогоняет `tools/static-check.py`
(имя файла, версия внутри, отсутствие тестового кода) и коммитит JAR вместе с
`release/sha256-<версия>.txt`. В папке всегда один JAR — актуальной версии.

**Запускайте workflow только после влития правок в `main`.** GitHub не даёт токену
Actions создать релиз на коммите, которого нет в ветке по умолчанию: будет
`403 Resource not accessible by integration`. А если указать HEAD самого прогона,
релиз создастся черновиком, без тега. Проверено 29.09.2026. В workflow есть шаг,
который заранее проверяет, достижим ли `target_sha` из `main`, и падает с понятным
сообщением, если нет.

Не забудьте указать `run_id` — номер прогона `Build`, который собрал именно этот
коммит (после мержа в `main` запустится новый `Build`, его номер и берите).

## Автоматические проверки на GitHub

В репозитории есть два workflow (`.github/workflows/`). Папку с точкой браузер при
перетаскивании файлов не загружает, поэтому её нужно создать через
**Add file → Create new file** и вписать полный путь в поле имени.

| Workflow | Когда запускается | Что делает |
|---|---|---|
| `build.yml` | на каждый push и pull request, плюс вручную | статические проверки `tools/static-check.py`, затем `./gradlew build` — это сборка и 36 unit-тестов; собранный мод выкладывается артефактом `settledlands-jar` |
| `smoke.yml` | вручную и на push в `main` при изменении `src/**` | поднимает настоящий выделенный сервер и выполняет **117 интеграционных проверок** (119 при повторе на том же мире); журнал и маркер результата выкладываются артефактом `smoke-log` |
| `publish-release.yml` | только вручную (**Actions → Publish release → Run workflow**) | берёт JAR из артефакта указанного прогона `Build`, создаёт релиз с тегом на нужном коммите и дописывает в описание размер и sha256 выложенного файла |

Запуск вручную: вкладка **Actions** → выбрать workflow → **Run workflow**.

Как читать результаты:

- зелёная галочка у `Build` — статические проверки, сборка и 36 unit-тестов прошли; на
  странице прогона (**Summary**) печатается размер и отпечаток `sha256` собранного JAR —
  по нему можно сверить файл у себя, не доверяя описанию на слово. Если в репозитории
  лежит готовый JAR (`dist/` или `release/`), отдельный шаг честно пишет в сводку,
  совпал он байт в байт или нет (расхождение сборку не роняет);
- зелёная галочка у `Integration suite` — прошли все 117 проверок на сервере (119 при
  повторном запуске на том же мире); в сводке прогона печатается маркер, в артефакте
  `smoke-log` лежит журнал со строками `CHECK OK`, маркер и `table-report.txt`;
- красный крест — откройте лог шага, в конце будет причина; для интеграционного набора
  смотрите строку `SANCTITY SMOKE FAILED` и текст ошибки под ней.

Оформление workflow: система закреплена как `ubuntu-24.04` (метка `ubuntu-latest` с

дождитесь результата, при необходимости приложите журнал из артефакта.

## Продолжение работы в новом ИИ-диалоге

Скопируйте такой текст:

> Продолжаем мод Settled Lands (Minecraft 1.21.1, NeoForge 21.1.252, Java 21).
> Репозиторий приложен, начни с `AI-HANDOFF.md` — там состояние, карта кода и решения.
> Собери проект (`CI=true ./gradlew build --no-daemon`) и при необходимости прогони
> интеграционные проверки (`CI=true ./gradlew runServer -PsanctitySmoke --no-daemon`).
> Дальше моя задача: <опишите, что нужно сделать>.

Приложите к сообщению архив репозитория или файлы `AI-HANDOFF.md` и `src/`.
Сборка требует **JDK 21**; в конфиге уже стоит ограничение памяти под слабые машины.
